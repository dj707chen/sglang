## The mental model

Three independent things, often conflated:

| Layer | What it is | Where it lives | Shared? |
| --- | --- | --- | --- |
| 1. The config | `.pre-commit-config.yaml` — declares repos, pinned revs, hook ids | repo root | **Yes**, checked in |
| 2. The tool | the `pre-commit` executable | `~/.local/bin/pre-commit` (uv tool) | No, per machine |
| 3. The git hook | `.git/hooks/pre-commit` shim | `.git/hooks/` | **No**, never tracked |

Checking in the config does **nothing** on its own. Layer 3 is what makes commits
run hooks, and it is created only by `pre-commit install`. Disabling is therefore
a purely local act — it cannot affect CI or other contributors.

Do **not** `pip install pre-commit` into `studyIterations/venvs/mps-py312` — that
venv was made by `uv venv` and has no `bin/pip`. `pre-commit` is a developer tool,
not an sglang runtime dependency, so it belongs in `uv tool` on PATH anyway.

Black is likewise **never** pip-installed. `pre-commit` builds an isolated
virtualenv per hook repo under `~/.cache/pre-commit/`, pinned to the `rev:` in the
config (black 26.1.0). `which black` correctly reports "not found" — that is
expected, not a broken install.

## Why the hook must be on PATH

The generated `.git/hooks/pre-commit` is a shim that shells back out to the tool:

```bash
#!/usr/bin/env bash
# File generated by pre-commit: https://pre-commit.com
INSTALL_PYTHON=/Users/WChen/.local/share/uv/tools/pre-commit/bin/python
ARGS=(hook-impl --config=.pre-commit-config.yaml --hook-type=pre-commit)
...
if [ -x "$INSTALL_PYTHON" ]; then
    exec "$INSTALL_PYTHON" -mpre_commit "${ARGS[@]}"
elif command -v pre-commit > /dev/null; then
    exec pre-commit "${ARGS[@]}"
else
    echo '`pre-commit` not found.  Did you forget to activate your virtualenv?' 1>&2
    exit 1
fi
```

It hardcodes the absolute interpreter path captured at install time, with a PATH
lookup as fallback. This is why an ephemeral `uvx pre-commit install` is a bad
idea: the shim would point into a cache entry that can be garbage-collected.

## Enable / disable

```bash
pre-commit install       # create .git/hooks/pre-commit  -> hooks run on every commit
pre-commit uninstall     # remove it                     -> commits run no hooks
```

Only the `pre-commit` hook type was ever installed here; `pre-push`,
`commit-msg`, `prepare-commit-msg`, `post-checkout`, `post-commit`, and
`post-merge` were checked and were absent. (`install` installs only the
`pre-commit` type by default, despite the config's
`default_stages: [pre-commit, pre-push, manual]`.)

Verify state at any time:

```bash
ls .git/hooks | grep -v '\.sample$'    # prints "pre-commit" when enabled, nothing when not
git config --get core.hooksPath        # should be unset
```

## Running it manually (no hook required)

This is usually the sweet spot: get the formatting without commits being rejected.

```bash
pre-commit run --files python/sglang/srt/entrypoints/engine.py
pre-commit run --all-files
pre-commit run black-jupyter --all-files     # a single hook by id
```

## Escape hatches while the hook IS installed

```bash
SKIP=black-jupyter git commit -m "..."   # skip specific hook ids (comma-separated)
git commit --no-verify -m "..."          # skip all hooks  (-n)
```

## The behavior that surprises people

A pre-commit hook that **modifies** files does not silently fix your commit. It
**fails** the commit and leaves the rewritten file unstaged:

```
black....................................................................Failed
- files were modified by this hook
```

No commit is created. You must `git add` the reformatted file and commit again.
pre-commit never amends a commit for you. This two-step is the single most common
reason people disable the hook.

Also note `no-commit-to-branch` in the config: with the hook installed, commits
directly to the default branch are blocked. Feature branches like
`localRun260814_A` are unaffected.

## What's in the config

`.pre-commit-config.yaml` declares ~32 hook ids. Highlights:

- **Formatters that rewrite files** (these are the ones that fail commits):
  `black-jupyter` (psf/black rev 26.1.0), `isort` (7.0.0), `ruff` (v0.15.1, with

  `check-merge-conflict`, `detect-private-key`, `debug-statements`,
  `check-added-large-files` (`--maxkb=1500`), `codespell`, `lychee`,
  `mint-broken-links`.
- **sglang-specific repo policy:** `forbid-docs-new-path`,
  `check-chinese-characters`, `sort-ci-permissions`, `check-workflow-job-names`,
  `check-rust-ext-cache-prefix`, `check-registered-tests`,
  `check-no-registered-tests-in-package`, `clippy-rust-workspace`.
- **Branch guard:** `no-commit-to-branch`.

Black uses its default line length of **88** — there is no `line-length` override
anywhere in `pyproject.toml`. That 88 is what forces the parenthesized
line-continuation style seen throughout `python/sglang/srt/`.

## First-run cost

The environments are already built in `~/.cache/pre-commit/`, so runs are fast
now. On a cold cache the first `pre-commit run` builds one virtualenv per repo
(black, isort, ruff, clang-format, rust toolchains, …) and takes a minute or more.
